# Wytyczne: k6 / testy obciążeniowe

## Cel

- Test obciążeniowy odpowiada na pytania eksperymentu: zachowanie PostgreSQL przy równoczesnych zapisach i cięższych odczytach, wpływ podziału zasobów, wpływ umiejscowienia logiki, realne granice pojedynczego serwera
- Wynik to dane do decyzji — każdy przebieg jest zapisywany, nie oglądany i zapominany

## Dane syntetyczne

- Generator danych syntetycznych jest CZĘŚCIĄ rozwiązania (kod w repo), nie skryptem ad-hoc
- Generowanie deterministyczne (seed) — ten sam seed = ten sam zbiór danych
- Wolumen parametryzowany; scenariusze odzwierciedlają realne proporcje operacji (odczyt/zapis)

## Scenariusze

- Skrypt k6 w repo, wersjonowany razem z kodem, uruchamiany taskiem
- Jawne fazy: ramp-up → steady state → (opcjonalnie) stress; pomiar wyłącznie ze steady state
- Progi (`thresholds`) w skrypcie: p95 latencji, error rate — przebieg zielony/czerwony automatycznie, nie "na oko"
- Ruch przez publiczne wejście (Caddy), nie bezpośrednio na kontener aplikacji — mierzysz system, nie fragment

## Porównywanie wariantów (kluczowe)

- Porównywane implementacje MUSZĄ zachowywać tę samą semantykę biznesową — test mierzy różnicę architektoniczną, nie przypadkowo różne zachowanie systemu
- Kontroluj liczbę zapytań do bazy w każdym wariancie — inaczej wynik opisuje liczbę wywołań, a nie miejsce, w którym mieszka logika
- Jeden zmienny czynnik na eksperyment; identyczne dane (ten sam seed) i identyczny profil obciążenia
- Maszyna z dedykowanym CPU; podział zasobów baza/aplikacja odnotowany przy każdym przebiegu

## Pomiar i wyniki

- Mierz z k6: latencję (p50/p95/p99), przepustowość, błędy; równolegle po stronie serwera: CPU, RAM, IO i metryki PostgreSQL
- Wynik przebiegu zapisywany (JSON summary + warunki: commit, seed danych, podział zasobów, profil obciążenia) — np. `perf-results/` w repo lub artefakt CI
- Minimum dwa przebiegi na wariant — pojedynczy pomiar to anegdota

## Czego unikać

- Load testu na współdzielonych rdzeniach CPU (obciążenie sąsiadów leży na osi pomiaru)
- Porównywania przebiegów o różnych danych, wolumenie lub profilu obciążenia
- Uśredniania wszystkiego — odpowiedź często niesie ogon latencji (p99)
- Generowania obciążenia z tej samej maszyny co system przy pomiarach granicznych (klient k6 konkuruje o CPU) — zawsze odnotuj, skąd generowano
